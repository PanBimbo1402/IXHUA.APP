Native-only capabilities must be clearly labeled as requiring Native Device Beta and must never be simulated and presented as validated.

This gate is part of the Release Candidate acceptance criteria. It does not weaken the native production requirement in Section 19, the owner approval gate in Section 176, or any product requirement elsewhere in this directive.

### One owner entry point

At the extracted project root, provide START-IXHUA.bat for Windows and an appropriate launcher for other supported development hosts. The Windows path must avoid requiring a PowerShell execution-policy change. Detect prerequisites and explain a missing runtime in plain language. Include the actual required application source, assets, runtime dependencies or reproducible lockfile-based setup, configuration templates and backend code.

Launching START-IXHUA must build the actual application when necessary, start every service needed by that implementation, verify readiness, and show a readable QR code in an automatically opened local page. A terminal QR is useful as an additional option. Do not display a success state merely because a process was spawned. If the backend, app, a required asset or a required service failed, show the failure and recovery step.

### Real application and backend

The phone must use the same application modules, programming rules, persistence implementation, media manifest and real API routes as the Release Candidate. A web preview target is permitted for owner review; it is not the final native app or evidence that a WebView wrapper meets the native requirement. Do not maintain a separate mock mobile product, hard-coded preview responses, fake logs, fake media or substitute workflows that cannot exercise the real implementation.

The QR link must point to an address the physical phone can reach. Do not encode localhost, 127.0.0.1 or 0.0.0.0 as the phone address. Detect the actual local Wi-Fi/Ethernet address, handle multiple adapters, and explain same-network requirements. Include copyable fallback instructions without forcing the owner to discover an IP address manually. If local preview cannot be reached, diagnose the issue; do not silently publish the app or create a public tunnel.

### Transport, persistence and honest boundaries

State whether the chosen preview uses local HTTP, trusted HTTPS, or an explicitly authorized private development transport. Do not claim HTTP provides encryption. Do not weaken device security, disable certificate checks or firewall protections, or expose privileged development APIs to the public internet as a shortcut. Secrets remain on the server. Access links must be local/temporary or otherwise access-controlled and must not use a third-party QR-generation service that receives owner access credentials.

Workout and food record IDs must still work correctly. Use real upload/manual workflows where appropriate; clearly label any browser camera, offline-installation or other transport limitation.
